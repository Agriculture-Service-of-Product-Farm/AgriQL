Why AgriQL exists

Agricultural records are full of numbers that look alike and are not alike. Twenty-five can be millimetres of rain, percent soil moisture, or kilograms of fertiliser. A spreadsheet will add them. A general-purpose database will store them and leave the mistake to a later script.

The unit stays with the value

AgriQL rejects a calculation that mixes incompatible units. Millimetres and kilograms are not added. Millimetres and metres can be added, because both are length. The check belongs with the record, where it is harder to skip.

One file for the season

Soil readings, crop notes, water, and weather for a farm or a field trial belong together. AgriQL keeps them in one .aqdb file. That file can be copied, archived, and opened again. Removing the program does not delete it.

The workbook is not the archive

People already work in Excel, Python, and R. AgriQL can take a table from CSV, TSV, JSON, or Excel, and it can write a table back out. An import records the file the rows came from, so a later reader can see that they were not typed in by hand.

If a notebook is lost, the database file is still the record. The analysis tool is allowed to change. The archive should not have to.

What this is not for

AgriQL is not a database for every application. Use it when the thing you need to trust is an agricultural measurement. A shop, a ledger of invoices, or a general website does not need it.
