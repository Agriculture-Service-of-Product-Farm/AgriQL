Why AgriQL is important

A farm record is a set of measurements, not a set of bare numbers. Rain, soil moisture, fertiliser, irrigation, and a crop note can sit in the same table and look interchangeable. They are not. AgriQL exists so that mistake is caught in the record, and so a season does not fall apart across files that no longer agree.

The same numeral is not the same quantity

Twenty-five millimetres of rain, twenty-five percent moisture, and twenty-five kilograms of fertiliser are three different statements. A spreadsheet will add them. A general-purpose database will store them as numbers and add them if a later query asks. The person who made the table may have known the difference. The person who opens it next year may not.

AgriQL keeps the unit with the value. It rejects a length added to a mass. It accepts millimetres added to metres, because both are length. The check is not a note in a cell. It is part of using the file.

A season should be one file

Soil, crop, water, and weather for one farm or one field trial belong together. AgriQL keeps them in a single .aqdb file. That file can be copied, handed to someone else, and opened again. There is not a folder of versions whose names say “final” and “final-2”.

Removing the program does not delete the file. The record outlives the particular machine it was written on.

You can see where the rows came from

An import from CSV, TSV, JSON, or Excel records the source file. A later reader can see that the rows were brought in, not typed as if they had no origin. That matters when a moisture reading is questioned: the table and the file it came from are still connected.

Trust the figure before you act on it

An average hides empty rows and odd values. AgriQL can profile a table and report those. It can also count gaps along a time column, which is the difference between a sensor that reported all season and one that went quiet for a week. A gap is not a reading of zero. Treating it as one changes the average.

A summary in this release reads one table. It can count, and it can take a minimum, a maximum, an average, and a standard deviation, with a filter and a grouping. It does not join several tables. That limit is stated because a joined figure that the software cannot produce should not be assumed.

The tools you already use stay outside the record

Excel, Python, and R are how many people study a season. AgriQL can write a table back out to CSV, TSV, JSON, or Excel, and the Python, R, and Arrow clients can take rows. They are not a second copy of the database. If the notebook is lost, the .aqdb file is still the record. The analysis tool is allowed to change. The archive should not have to.

Where it is the wrong tool

AgriQL is not important for a shop, an invoice ledger, or a general website. It does not read Parquet, and it does not read a spreadsheet that exists only online. Use it when the thing you need to trust is an agricultural measurement, and when mixing those measurements up would matter.
